# 『AI Character OS 초기 개발 계획서 v0.1』 검토

검토자: Phase 0 PoC 구현 과정에서 나온 관점
검토 기준: 이 계획서를 그대로 실행했을 때 Phase 0~2가 실제로 끝나는가

---

## 0. 총평

방향은 옳습니다. 특히 세 가지 결정은 이 문서의 핵심 자산입니다.

1. **캐릭터와 LLM의 분리.** "GPT는 캐릭터가 아니라 외부 추론 엔진"이라는 한 문장이 이 프로젝트의
   수명을 결정합니다. 구현해 보니 실제로 provider를 바꿔도 정체성·기억·관계가 그대로 유지되는
   구조가 나왔습니다. 이 원칙이 없으면 제품은 특정 모델사의 래퍼가 됩니다.
2. **Local-first.** 기술 선택이 아니라 제품 포지션입니다. 경쟁 서비스가 따라 하기 가장 어려운 지점이고,
   규제(개인정보·생체정보) 측면에서도 유일하게 방어 가능한 자리입니다.
3. **Rule-based Behavior Primitive 우선.** 옳습니다. 구현해 보면 '교감하는 느낌'을 만드는 것은
   감정 분류 정확도가 아니라 **반응 지연·시선 유지 시간·호흡**이라는 게 바로 드러납니다.
   ML 없이도 여기까지 검증됩니다.

다만 **계획서 전체가 "무엇을 만들 것인가"로만 되어 있고, "무엇을 충족하면 다음 단계로 간다"가
거의 없습니다.** Phase 0~7이 각각 끝났다고 판단할 기준이 없어서, 현재 상태로는 Phase 0이 무한히
길어질 수 있는 구조입니다. 아래 지적의 상당수가 여기서 파생됩니다.

## 1. 지금 당장 계획서에 추가해야 할 것 (우선순위 순)

### 1-1. Latency 예산이 없다 — Phase 0 최대 리스크

계획서 어디에도 응답 시간에 대한 숫자가 없습니다. 그런데 "살아있는 존재처럼 느끼는가"는
거의 전적으로 타이밍 문제입니다. 사람은 상대가 **300ms 안에 아무 반응(시선·호흡·표정)도**
하지 않으면 그 순간 '기계'로 판정합니다. 반면 LLM 왕복 + TTS 합성은 통상 1.5~4초입니다.

6장의 `speech_delay: 1.2`는 좋은 아이디어지만, **지연을 숨기는 장치가 아니라 지연 위에
연출을 더 얹는 장치**입니다. 실제 지연이 2초인데 거기에 1.2초를 더하면 3.2초가 됩니다.

필요한 것은 **2단 응답 구조**입니다.

```
사용자 발화 종료
  ├─ 0~300ms : 로컬이 즉시 비언어 반응 (시선 복귀, 눈 깜빡임, 작은 끄덕임, 숨)  ← LLM 없음
  ├─ ~800ms  : 로컬이 필요하면 간투사 수준의 즉답 ("음—", "어")
  └─ 1~3s    : LLM 문장 도착 → 문장 단위 스트리밍 TTS
```

현재 PoC는 이 구조의 앞쪽 절반(로컬 비언어 반응 + speech_delay 연출)을 구현해 두었습니다.
계획서에는 다음을 명시할 것을 권합니다.

- Phase 0 종료 조건에 수치 추가: **발화 종료 → 첫 비언어 반응 ≤ 300ms, 첫 음성 ≤ 1.5s (p50)**
- 구간별 예산표: Perception ≤ 100ms / Decision ≤ 50ms / Provider ≤ 800ms(p50)·2s(p95) / TTS 첫 오디오 ≤ 300ms
- LLM 응답 스트리밍과 문장 단위 TTS를 Phase 0 범위에 포함 (지금은 범위 밖으로 읽힘)

### 1-2. 성공 기준(15장)이 측정 불가능하다

"사용자가 캐릭터를 '나를 인식하고 반응하는 존재'처럼 느끼는가" — 이건 목표이지 지표가 아닙니다.
이 문장만으로는 누구도 "됐다/안 됐다"를 말할 수 없습니다. 측정 가능한 프록시를 제안합니다.

| 지표 | 왜 이것인가 |
|---|---|
| 7일 재방문율 | '존재감'의 가장 정직한 대리 지표 |
| 세션당 자발 발화 수 | 질문에 답하는 게 아니라 먼저 말을 거는가 |
| 재회 인식 테스트 통과율 | 3일 뒤 다시 켰을 때 이전 맥락을 꺼내는가 (기억 계층의 직접 검증) |
| 비언어 A/B | **반응 지연·시선 추종·호흡을 끈 빌드 vs 켠 빌드**의 위 지표 차이 |

특히 마지막 A/B는 Phase 0의 진짜 질문입니다. 이걸 돌리려면 Behavior Engine에 **기능별 on/off
토글**이 있어야 하므로, 계획서 Phase 0 산출물에 "Behavior 요소별 토글과 A/B 로깅"을 넣어야 합니다.

### 1-3. Privacy 원칙은 있는데 '전송 계약'이 없다

5장은 무엇을 보내지 **않는지**는 잘 적었지만, 무엇을 보내는지의 **상한**이 없습니다.
원칙은 시간이 지나면 침식됩니다("이번만 컨텍스트를 조금 더 주면 품질이 오르는데").
필요한 것은 문서가 아니라 **코드로 강제되는 화이트리스트**입니다.

- 전송 payload를 스키마로 고정하고, 스키마에 없는 필드는 전송 계층에서 폐기
- 관계는 수치 원본(`affection: 0.81`)이 아니라 **단계 라벨**("가까운 사이")로만 전송
  → 수치를 매 턴 보내면 외부에서 관계 곡선을 복원할 수 있습니다. 재식별 위험입니다.
- 전송 바이트 상한 + 사용자에게 전송 원문을 그대로 보여주는 감사 화면

PoC에서는 `brain/privacyFilter.js` + Privacy 탭으로 이 형태를 구현해 두었습니다.

**그리고 계획서와 현실이 충돌하는 지점이 하나 있습니다.**
5장은 "카메라/마이크 원본: 원칙적으로 Local 처리"라고 적었는데, 브라우저 Web Speech API(Chrome)나
대부분의 상용 STT는 **음성을 서버로 보냅니다.** 즉 음성 인식을 붙이는 순간 이 원칙이 깨집니다.
둘 중 하나를 골라 계획서에 명시해야 합니다.

- (a) 온디바이스 STT(Whisper 계열 등)를 Phase 2 필수 항목으로 승격, 또는
- (b) "음성 인식은 예외이며 사용자에게 명시적으로 고지하고 동의받는다"를 원칙에 기재

지금처럼 비워두면 나중에 조용히 (b)가 되고, Local-first라는 포지션의 신뢰가 무너집니다.

### 1-4. 구조화 응답의 '최종 결정권'이 명시되지 않았다

6장은 "구조화된 데이터로 반환받는다"까지만 말합니다. 그런데 `affection: 0.81`을 LLM이 돌려줬을 때
**그 값을 그대로 쓸 것인지**가 정해져 있지 않습니다. 그대로 쓰면 관계가 매 턴 요동칩니다.
모델을 바꾸면 인격도 바뀝니다. 이는 14장 "Character Continuity"와 정면으로 충돌합니다.

원칙으로 명문화할 것을 권합니다.

> **LLM은 제안하고, Character Brain이 결정한다.**
> 외부 모델의 emotion / affection 값은 제안치이며, 로컬이 성격 파라미터와
> 턴당 최대 변화폭으로 clamp한 뒤에만 상태에 반영된다.

PoC 구현: `applyEmotion()`이 성격의 정서 안정성으로 감정 반전을 완충하고,
`clampProposedAffection()`이 애정도 변화를 한 턴 ±0.04로 제한합니다.

### 1-5. Character Continuity(14장)가 데이터 모델로 정의되어 있지 않다

"LLM이나 Body가 바뀌어도 동일한 존재를 유지"는 비전 문장으로만 있고, 그걸 보장하는 **포맷**이
없습니다. 이건 나중에 붙일 수 없는 종류의 것입니다 — 스키마를 먼저 고정하지 않으면 Phase 3쯤에서
기억 마이그레이션이 불가능해집니다.

Phase 1 완료 조건에 다음을 넣을 것을 권합니다.

- **Character Save Format v0 스펙**: Identity / Personality / Memory / Relationship의 직렬화 포맷과 버전 필드
- 버전 마이그레이션 테스트 (v0 데이터 → v1 코드로 로드했을 때 관계·기억이 보존되는가)
- Body 교체 시뮬레이션 테스트 (2D → 다른 렌더러로 같은 상태를 로드)

### 1-6. 로컬 저장의 '상실 리스크'가 과소평가되어 있다

5장은 서버를 "선택적 암호화 동기화 중심"이라고 적었습니다. 그런데 관계 데이터는 사용자에게
**감정적 자산**입니다. 기기를 바꾸거나 브라우저 데이터를 지워서 캐릭터가 '죽으면' 그 사용자는
돌아오지 않습니다. 이건 부가 기능이 아니라 리텐션의 전제 조건입니다.

→ **E2EE 백업/복구를 Phase 1 필수**로 승격할 것을 권합니다(서버는 복호화 불가, 키는 사용자 보유).
Local-first와 모순되지 않습니다. 오히려 Local-first를 지속 가능하게 만드는 쪽입니다.

### 1-7. 안전·윤리 항목이 통째로 빠져 있다

장기 관계형 캐릭터에서 이건 선택 사항이 아닙니다. 그리고 이 계획서의 구조는 특히 조심해야 합니다 —
**affection을 올리는 방향으로만 설계된 보상은 자연스럽게 '사용자를 붙잡는 쪽'으로 최적화됩니다.**
8장의 "사용자가 어떻게 변화했는지"를 학습 신호로 쓰겠다는 설계는 강력한 만큼 이 위험도 큽니다.

Phase 1에 최소한 다음을 넣을 것을 권합니다.

- 위기 발화(자해·자살 언급 등) 감지와 전문 리소스 안내로의 핸드오프 경로
- 미성년 사용자 정책
- 설계 원칙 명문화: **관계 수치를 사용자에게 게임화된 목표로 노출하지 않는다**
- 학습 목표 함수에 "체류 시간"을 직접 넣지 않는다는 원칙

### 1-8. 비용 구조가 Phase 6로 너무 늦게 밀려 있다

Phase 6 "Local AI: 소형 온디바이스 LLM로 일상 대화 처리"는 방향은 맞지만 **시점이 늦습니다.**
매 턴 클라우드 LLM을 호출하면, Phase 2~3의 반복 실험 자체가 비용 제약을 받습니다
(실시간 교감 실험은 짧은 턴을 대량으로 돌려야 하는 성격입니다).

→ **라우팅을 Phase 1로 당길 것**을 권합니다. 완전한 온디바이스 LLM이 아니라,
"로컬 룰/소형 모델이 먼저 처리하고, 어려운 것만 클라우드로" 정도의 2단 라우팅이면 충분합니다.
PoC의 로컬 룰 엔진이 그 자리의 원형입니다(키 없이도 전체 루프가 돌아갑니다).

## 2. 기술 판단에 대한 의견

### 2-1. Seedance 등 생성영상 Teacher 전략(10장)

라이선스 검토를 명시한 건 좋습니다. 다만 **더 큰 문제는 라이선스가 아니라 분포 편향**입니다.

생성 영상과 연출 데이터는 "연출된, 정면의, 의미 있는 순간"에 치우쳐 있습니다. 그런데 실제 교감에서
존재감을 만드는 건 대부분 **지루한 구간**입니다 — 딴짓, 곁눈질, 무반응, 어색한 침묵, 말 끊김,
상대가 말하는 동안의 미세한 무표정. 이건 연출된 영상에 거의 들어있지 않습니다.
Teacher를 여기서만 뽑으면 캐릭터가 "항상 연기 중"인 상태가 되고, 그건 빠르게 피로해집니다.

또한 생성 영상에서 추출한 tracking은 오차가 누적되는 2차 데이터입니다.

→ 11장의 데이터 우선순위를 다음으로 재배치할 것을 권합니다.

```
현재 순서: Human → Directed Acting → Synthetic → Director Feedback
권고 순서: Director Feedback  ≫  Human Interaction  >  Directed Acting  >  Synthetic
```

**Director Feedback(사람이 "시선을 0.3초 더 유지" 하고 고친 기록)이 가장 값비싸고 가장 희소한
자산입니다.** 이건 다른 데서 살 수 없고, 축적되면 그 자체가 해자가 됩니다.
반면 Synthetic은 언제든 다시 만들 수 있으므로 우선순위가 가장 낮습니다.

### 2-2. 감정 5개 (13장)

적절합니다. 다만 **감정 라벨 수를 늘리는 것보다, 같은 감정 안에서 표현 강도를 관계 단계에 따라
다르게 만드는 쪽이 체감 차이가 훨씬 큽니다.** 9장이 이미 그렇게 적혀 있으니, 13장의
"5개 내외 감정 상태"가 라벨 확장 압력으로 읽히지 않도록 "감정 라벨은 5개로 고정하고,
표현 변주는 관계·성격 파라미터로 만든다"고 못 박는 편이 낫습니다.

### 2-3. Phase 1과 Phase 2의 순서

Phase 2(실시간 교감)를 Phase 1(Brain) 뒤에 둔 것은 재검토가 필요합니다.
**Perception 신호는 Brain의 인터페이스를 바꿉니다.** 예를 들어 "사용자가 화면 앞에 없음"은
Motivation 결정에 직접 들어가는 입력입니다. Brain을 다 만든 뒤에 Perception을 붙이면
Motivation/Decision 계층을 다시 설계하게 됩니다.

→ 최소 Perception(얼굴 존재 여부 / 발화 여부) 두 가지만이라도 Phase 1로 당길 것을 권합니다.
PoC는 그렇게 구성했고, 실제로 Motivation 규칙이 Perception 입력을 전제로 짜였습니다.

### 2-4. 3장 아키텍처 다이어그램의 누락 화살표

현재 다이어그램은 단방향입니다.

```
Character Brain → Decision → AI Provider → Behavior Engine → Digital Character
```

그런데 실제로는 **Behavior Engine이 끝나기 전에 Brain이 다음 상태로 넘어가면 안 됩니다**
(말하는 도중에 감정이 바뀌면 표정과 음성이 어긋납니다). 또 사용자가 캐릭터의 말을 끊는 경우
(barge-in)도 현재 다이어그램에 표현되어 있지 않은데, 이건 실시간 교감에서 매우 흔한 상황입니다.

→ 다이어그램에 (a) Behavior 완료 → Brain 커밋, (b) 사용자 발화 감지 시 Behavior 중단(barge-in)
두 경로를 추가할 것을 권합니다. Barge-in 처리는 Phase 2의 명시적 항목이 되어야 합니다.

## 3. 문서 자체에 대한 의견

- **Phase별 완료 조건(Exit Criteria)이 없습니다.** 12장의 각 Phase에 "무엇이 되면 끝인가"를
  한 줄씩만 붙여도 문서의 실행력이 크게 올라갑니다.
- **팀/기간/비용에 대한 언급이 없습니다.** 초기 개발 계획서라면 Phase 0~2의 인력 구성
  (렌더링 1, 시스템 1, 연출/데이터 1 등)과 기간 추정이 있어야 의사결정에 쓸 수 있습니다.
- **경쟁/대안 분석이 없습니다.** 특히 "왜 지금 이 조합인가"(온디바이스 성능·LLM 단가·생성영상 품질이
  교차하는 시점)를 한 문단이라도 넣으면 타이밍 논거가 생깁니다.
- 16장의 장기 비전(Body 교체)은 훌륭하지만, 지금 단계에서는 **14장 Character Continuity의
  데이터 포맷으로 환원**해서 서술하는 편이 실행 가능합니다.

---

## 4. 요약 — 계획서 수정 제안 6가지

1. Phase 0 종료 조건에 **latency 수치**를 넣고, 2단 응답(로컬 즉시 비언어 → LLM 문장) 구조를 명시
2. 15장 성공 기준을 **측정 가능한 지표 + 비언어 A/B**로 재작성
3. "LLM은 제안, Brain이 결정" 을 **개발 원칙(2장)에 추가**
4. Privacy를 원칙이 아닌 **전송 스키마 화이트리스트 + 감사 화면**으로 구체화하고,
   음성 인식의 로컬 처리 예외를 명시
5. 11장 데이터 우선순위를 **Director Feedback 최상위**로 재배치
6. **안전·윤리 장(章)을 신설**하고, E2EE 백업과 LLM 라우팅을 Phase 1로 승격

## 부록: 이 PoC로 확인된 것

- Rule-based primitive 10여 개만으로도 '반응하는 존재'의 느낌은 만들어집니다.
  결정적 요소는 감정 분류가 아니라 **반응 지연 + 시선 추종 + 깜빡임 분포 + 호흡**이었습니다.
- Provider를 Local ↔ GPT ↔ Claude로 바꿔도 기억과 관계가 유지되는 구조는 실제로 성립합니다.
  단, 그러려면 **상태 갱신 권한을 로컬이 독점**해야 합니다(1-4 참조).
- 외부 전송 컨텍스트는 생각보다 작아도 됩니다. 관련 기억 3~4건 + 관계 단계 라벨 + 감정 + 지각 요약이면
  충분한 응답이 나옵니다. 전체 대화 로그를 보낼 이유가 없습니다.
- 브라우저 TTS는 음성이 설치되지 않은 환경에서 `onstart`가 오지 않는 경우가 있습니다.
  이런 경우 캐릭터가 영구히 멈추므로, **음성 계층에는 반드시 워치독이 필요**합니다
  (PoC에서 `behavior/voice.js`에 구현).
